# Изолированный звуковой стенд

Это эксперимент с базовым тембром четырёхцилиндрового четырёхтактного двигателя.
Профиль не калиброван под Renault Logan/K7M. Физика автомобиля, её RPM и трансмиссия
в стенде не используются и не исправляются звуком. Пространственных эффектов,
салона, трафика, стартера, турбины и произвольных хлопков нет.

## Запуск исходников

Из корня проекта, Node.js 22.12+ или 24:

```sh
npm ci
npm run audio:dev
```

Открыть `http://localhost:5200/audio-lab.html`. Нажать «Включить звук»: до этого
действия пользователя AudioContext не создаётся. Вкладка запрашивает один
AudioContext и один AudioWorkletNode; повторное включение использует их снова.
При остановке выход плавно затухает, а после затухания вычисления ядра прекращаются;
узел и последнее состояние сохраняются. Mute отделён от отключения сгорания.

Через `?sr=44100` или `?sr=48000` выбирается запрос частоты. Сверять нужно фактическую
частоту в интерфейсе и журнале: запрос не является доказательством частоты устройства.
Сменить частоту существующего AudioContext нельзя; для смены перезагрузить вкладку.

## Запуск готовой сборки без npm

Готовая сборка находится в `dist-audio/`:

```sh
cd dist-audio
python3 -m http.server 5200 --bind 127.0.0.1
```

Открыть `http://localhost:5200/audio-lab.html`. Открытие HTML двойным нажатием через
`file://` не поддерживается: AudioWorklet нужны HTTP localhost или HTTPS.
Для самостоятельной сборки: `npm run audio:build`.

## Входы и время

`rpm` — об/мин коленвала, `load01` — заданная тестом интенсивность сгорания 0…1,
`combustionEnabled` — разрешение сгорания. Load не является измеренной нагрузкой
автомобиля или положением газа. Каждое сообщение имеет возрастающий `sequence`
и `atAudioTimeS` в секундах AudioContext; события имеют отдельный код.

При старте живого сценария `epoch = AudioContext.currentTime + 0.025`.
Сообщение рассчитывается для `atAudioTimeS = currentTime + 0.020`, а время сценария
равно `max(0, atAudioTimeS - epoch)`. Таким образом, начальные 25 мс — привязка
эпохи, 20 мс — запас доставки следующего значения. Процессор применяет команду
в первом отсчёте не раньше заданного времени. Фаза между командами не сбрасывается.
Запоздавшие команды моложе 250 мс применяются в ближайшем доступном отсчёте;
более старые и сообщения с неверной последовательностью отвергаются.

Дискретные события сценария планируются отдельно от частоты обновления параметров:
границы сгорания/переключений не должны исчезать между двумя редкими сообщениями.
Очередь упорядочена по аудиовремени; номер sequence проверяется при приёме и не
обязан возрастать в порядке применения команд с разными временными метками.
Блокировка основного потока всё равно может задержать отправку события.

Процессор сглаживает RPM с постоянной времени 20 мс, интенсивность — 15 мс,
разрешение сгорания — 2 мс, выходной уровень — 10 мс. Это постоянные времени
экспоненциального сглаживания, а не время полного завершения перехода.

В активном сценарии возраст данных считается от времени последней применённой
команды. После 250 мс начинается линейное приглушение на 100 мс; восстановление
также линейное на 100 мс. Запас доставки не делает блокировку главного потока
незаметной для реакции на физику: своевременность реакции проверяется отдельно
от непрерывной генерации. Сценарий не предсказывает физику во время блокировки.

В ручном режиме последнее заданное состояние не устаревает. «Пауза» приглушает
выход, не превращая остановленную передачу телеметрии в аварию; время сценария
при продолжении сдвигается на длительность паузы. Полной остановки механики
кнопка «Сгорание» не выполняет: при ненулевых RPM механический компонент остаётся.

OfflineAudioContext используется только для диагностического экспорта. Это не
второй одновременно звучащий AudioContext. В offline-режиме все команды заранее
расписаны на аудиошкале; тем самым такой экспорт сам по себе не проверяет доставку
через занятый главный поток. Для этой проверки существуют живые записи.

## Алгоритм и частота дискретизации

Начальная открытая основа: Antonio-R1/engine-sound-generator,
`c76c5adb9e63f5a54fb0def3b97e8e0ac1a7dea1`, MIT. База проекта:
`c9faa71a16fde48c2beb0db362189b82bb958149`. Полное уведомление MIT и неизменённая
исследованная версия сохранены в `docs/audio-reference/`.

Цилиндры сдвинуты равномерно по циклу 720°. Волноводы представляют акустические
задержки, а не автомобильную физику. Их задержки определены в секундах относительно
параметров исходного профиля при 44,1 кГц и реализованы дробными задержками с
интерполяцией. Коэффициенты фильтров и сглаживания рассчитываются из фактической
частоты. Фаза приращается на RPM/(120×sampleRate), длительность импульса задаётся
в градусах коленвала. Поэтому адаптация не ограничивается заменой константы фильтра.
Интерполяция задержек и конечная полоса фильтров всё же могут менять верхний тембр;
результаты сравнения частот не заменяют прослушивание.

Load меняет силу возбуждения камеры, угловую ширину импульса и относительную долю
впуска/выпуска. Механическое движение продолжает возбуждать систему при отключении
сгорания. Ограничитель уровня — гладкая ограниченная нелинейность с запасом по
амплитуде; соответствие −1 dBTP устанавливается анализом записей, а не этой формулой.

## Сценарии и проверки

В интерфейсе доступны 30 с холостого хода; подъём/спуск 750…5800 RPM;
2000/3500 RPM при load 0.1/0.5/1; отключение сгорания; заданные переключения и
отсечка; ступень для измерения реакции. Переключения и отсечка — тестовые события,
не модель коробки. Есть частоты обновления 15/30/60/120 Гц и намеренные блокировки
главного потока 100/500 мс.

Браузерные проверки с системным Chromium:

```sh
npm run audio:dev
# Во втором терминале, пока сервер работает:
npm run audio:check
```

При другом пути к Chromium задать `CHROMIUM_PATH`. По умолчанию результаты
пишутся в соседнюю папку `../engine-audio-results`; иной путь передаётся аргументом
`npm run audio:check -- /путь/к/результатам`. Playwright запускает настоящий
Chromium без обхода пользовательского запуска аудио; действие включения выполняет
нажатием кнопки. Диагностика исходного параметра газа отдельно:

```sh
node docs/audio-reference/check-throttle.cjs
```

Новые WAV — моно PCM24. JSON с тем же именем содержит `sampleRate`, `startFrame`,
число отсчётов, названия полей и строки телеметрии. Нулевая точка WAV — `startFrame`
AudioContext, его абсолютное аудиовремя — startFrame/sampleRate. Поле `sampleIndex`
отсчитывается от этого нуля. Телеметрия снимается примерно раз в 10 мс; отдельные
таблицы содержат все применённые команды и отсчёты событий сгорания. `framesSent`
в живых записях показывает отправку из главного потока, `appliedRows` — применение
в процессоре. Поля `requestedAudioTimeS` и `appliedAudioTimeS` позволяют отделить
доставку от сглаживания. Смысл eventCode задаёт `eventNames`.

В аудиопотоке нет файловых операций или подробных строковых логов. Во время записи
используются предварительно выделенные буферы, передаваемые после завершения.
Рендер ограничен 40 секундами на запись.

## Что результаты не доказывают

- Прослушивание исполнителем **не выполнено**; сходство с реальным двигателем
  и субъективная убедительность остаются открытыми.
- Счётчик непрерывности и PCM относятся к графу браузера. Физический выход,
  драйверные underrun/xrun и акустическая задержка не проверены.
- Время OfflineAudioContext измеряется настоящим браузером, но включает захват
  и обмен данными. Оно не равно изолированному времени DSP на живой аудиоблок.
- Автоматический анализ щелчков показывает кандидатов на разрыв; преднамеренные
  импульсы двигателя не позволяют доказать отсутствие слышимых щелчков одной метрикой.
- Совпадение частоты событий RPM/30 не требует, чтобы самый сильный спектральный пик
  имел эту частоту, и не доказывает реалистичность тембра.
- Рекомендация до прослушивания: оставить синтез экспериментальным кандидатом.
  Если нормализованные нагрузки звучат как один электронный гул, отвергнуть гипотезу
  и искать записи; генерированные лупы такой недостаток не исправят.

## Карта изменённых файлов

- `src/audio/engine-dsp.js` — синтез; `engine-worklet.js` — аудиочасы, команды,
  устаревание и захват; `fixtures.js` — сценарии; `lab.js` и `lab.css` — стенд.
- `audio-lab.html` — отдельная страница; `vite.audio.config.ts` и три scripts
  `audio:*` в `package.json` — изолированный запуск/сборка/проверки.
- `tools/audio-check.mjs` — Chromium-проверки; `tools/audio-analysis.py`, если
  включён в итоговую поставку, — внешний анализ WAV после завершения записи.
- `docs/audio-reference/*` — MIT, зафиксированный upstream и прежняя диагностика.
- `docs/audio-lab.md`, новый блок `STATE.md` и игнорирование `dist-audio/` —
  воспроизводимость и состояние. Игровые исходники не изменялись.
